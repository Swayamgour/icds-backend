# Field Workforce Monitoring Backend (Suposhit Dahod Program)

District (Manager) → Block (CDPO) → Supervisor (1 per sector) → Sector (Mukhya Sevika) → AWC (Worker)
hierarchy, built to match the tender: GPS check-in, geo-tagged photo proof,
task assignment, approve/reject workflow, an auto-grading engine, and
Excel/PDF reports.

## Setup

```bash
cd icds-backend
npm install
cp .env.example .env       # fill MONGO_URI and JWT_SECRET
npm run seed                # loads Dahod district data + 1 demo user per role
npm run dev                 # or: npm start
```

`npm run seed` prints the 4 demo logins (district/block/sector/awc) it creates
- see "Seeded demo data" below.

## Hierarchy & Roles

```
District (PO/DDO)  -> "Manager"
   └── Block (CDPO)
         └── Supervisor            -> exactly 1 per sector (role: "supervisor")
               └── Sector (MS)     -> "Mukhya Sevika"
                     └── AWC (Worker)
```

## What each piece is for

| Feature | Tender requirement it covers |
|---|---|
| GPS check-in/out on every submission | "GPS-based check-in/out" |
| Photo proof (`photos[]` with lat/lng + timestamp) | "Photographic documentation with geo-tag and timestamps" |
| `Task` + `TaskSubmission` | "Task list with due dates" + "Task assignment to individuals/groups" |
| `status: pending/approved/rejected` on every submission | "Approve/reject entries" |
| `Grade` model + auto-grading engine | "Automate performance grading", "Grading engine" |
| `Notice` (auto-created on C/D grade) | "Autogenerated notice system" |
| `/api/reports/*` (Excel/PDF) | "Export in Excel/PDF" |
| `/api/reports/heatmap` | "Regional heat maps and data visualization" |
| Sector-wise `/api/dashboard` | "Sector-level comparisons... high/low performing centers" |

**Not built (flagged as genuinely out of scope or needing a separate
decision):** AI-based image validation and headcount-in-photo (tender lists
AI validation as **Out of Scope**; headcount is listed as an *optional add-on*
under "Additional Components" — needs a computer-vision service, not just an
API, so it's a separate scoping conversation). Offline mobile sync is a
mobile-app concern; this API is stateless/idempotent-friendly so it supports
a sync queue, but the queue itself lives in the app.

## Data entry vs computed views

- **Worker Detail Entry** (`/api/records`) — AWC worker's own daily entry,
  now with GPS check-in and photo proof.
- **Mukhya Sevika Detail** (`/api/mukhya-sevika`) — Sector Supervisor's AWC
  visit log, GPS + photo proof.
- **Tasks** (`/api/tasks`, `/api/task-submissions`) — admin assigns work with
  a due date, to one user or a whole group; field staff submit completion
  with GPS + photo; admin reviews.
- **Dashboard** (`/api/dashboard`) — NOT manually entered, live sector-wise
  rollup computed from Worker entries.
- **Grades** (`/api/grades`) — NOT manually entered by default. Computed from
  punctuality (days submitted), submission quality (approval rate),
  beneficiary ratio (actual vs registered), and task completion rate.
  Admin can override any sub-score.
- **Notices** (`/api/notices`) — auto-created whenever a monthly grade comes
  out C or D.

## Role-based visibility

Enforced everywhere by `req.scopeFilter` (`middleware/scopeFilter.js`):

| Role     | Sees |
|----------|------|
| district | Everything in the district; only role that can create users, delete users, generate district-wide grades |
| block    | Its own block's sectors/awcs/records/visits/tasks/grades/users |
| supervisor | Whole sector (one per sector): its awcs/records/MS visits/tasks/grades/users; reviews AWC records, MS visit logs, task submissions; creates sector/awc users; assigns tasks; generates grades |
| sector   | Its own sector's awcs; submits Mukhya Sevika visits; reviews AWC records |
| awc      | Only its own data; submits daily records; sees only its own grade |

## Supervisor role

- `role: "supervisor"`, exactly **one per sector** (unique DB index + friendly 400 error on a 2nd one).
- Login with email, **or** with `supervisorCode` = `SUP` + sectorCode (e.g. `SUP244450101`) - separate from the sector (MS) login, which still uses the plain sectorCode.
- Create one: `POST /api/users` as district/block - `{ name, email, password, role: "supervisor", sectorCode, blockCode? }`.
- Rank order is `district > block > supervisor > sector > awc` (`config/roles.js`), so a supervisor can create/assign tasks to/review sector (MS) and AWC users, and only block/district can review the supervisor's own task submissions.

## API Endpoints

All private routes need header: `Authorization: Bearer <token>`

### Auth
- `POST /api/auth/register` — bootstrap only: `{ name, email, password, role, districtCode, blockCode?, sectorCode?, awcCode? }`
- `POST /api/auth/login` — `{ email, password }` → `{ token, user }`
- `GET /api/auth/me`

### Hierarchy master data
- `POST/GET /api/hierarchy/district` (create: district only)
- `POST/GET /api/hierarchy/block` (create: district only)
- `POST/GET /api/hierarchy/sector` (create: district/block)
- `POST/GET /api/hierarchy/awc` (create: district/block/sector)

### Adding the real supervisors (Mukhya Sevika list)
`seed/supervisorData.json` holds the 122 supervisors from `MS_Details.xlsx` (one per sector, 21 blocks).
- `npm run seed:supervisors` - adds them (role `supervisor`, login `SUP<sectorCode>` or email). Does **not** wipe anything; run `npm run seed` first only if the hierarchy is empty.
- `npm run seed:supervisors -- --dry-run` - preview only. `-- --role=sector` adds them as the MS (`sector`) role instead. `-- --reset-passwords` re-issues passwords.
- Every supervisor gets the default password `pass1234` (login `SUP<sectorCode>`, e.g. `SUP244450105`). Set `SUPERVISOR_DEFAULT_PASSWORD` in `.env` to change it, or use `-- --random-passwords` for a different password each. The login list is written to `seed/supervisor-credentials.csv` (delete it after sharing).
- A demo supervisor made by `npm run seed` for the same sector is replaced; manually created supervisors are never overwritten. `npm run seed` later skips sectors that already have a real supervisor.

### Photo upload
- `POST /api/upload` — multipart form-data, field name `photos` (up to 10 files, JPEG/PNG/WEBP, 8MB each) → `{ files: [{ url, publicId, originalName, size }] }`. Files are saved inside the project's `uploads/` folder (no Cloudinary) and served at `<host>/uploads/<filename>`; set `BASE_URL` in `.env` if the public host differs from the request host. Attach the returned `url`s (with your own lat/lng) into a submission's `photos[]` array.

### Records — Worker Detail Entry
- `POST /api/records` (awc only) — `{ date, registeredChildrenCount, centerOpen, morningMealChildrenCount, morningDishPhoto, childrenEatingBreakfastPhoto, milkPouchGiven, milkPouchCount, afternoonMealGiven, afternoonMealChildrenCount, preEducationConducted, preEducationChildrenCount, poshanDishGiven, poshanBenefitGiven, photoBeneficiariesNutrition, qualityOfMeal, remarks, checkInLatitude, checkInLongitude, photos: [{url, latitude, longitude}] }`
- `GET /api/records?fromDate=&toDate=&status=` — auto-scoped
- `PATCH /api/records/:id/review` (sector/block/district) — `{ status: "approved"|"rejected", remarks }`

### Mukhya Sevika Detail — Sector Supervisor visit log
- `POST /api/mukhya-sevika` (sector only) — `{ awcCode, date, registeredChildrenCount, arrivalTime, checkInLatitude, checkInLongitude, photos }`
- `GET /api/mukhya-sevika?fromDate=&toDate=&status=` — district/block/sector
- `PATCH /api/mukhya-sevika/:id/review` (block/district) — `{ status, remarks }`

### Supervisor Visit - inspection form (Supervisor role)
Supervisor can visit **any AWC in her own sector** and fill the 4-section form
(General, Section A, Section B, Section C). Each section is saved on its own and
shows Completed + submitted time; once all 4 are completed the visit becomes `submitted`.
- `GET /api/supervisor-visits/prefill/:awcCode` (supervisor) - AWC name + registered children for pre-filling
- `POST /api/supervisor-visits` (supervisor) - `{ awcCode, date?, checkInLatitude?, checkInLongitude? }` starts a visit (returns the existing draft if one is already open for that AWC today)
- `PUT /api/supervisor-visits/:id/sections/:section` (the supervisor who started it) - `section` = `general | a | b | c`, body = that section's fields (see `models/SupervisorVisit.js`). `"markComplete": false` saves progress without marking it Completed. Photos: upload via `POST /api/upload` first, then send `{ url, publicId, latitude, longitude }`.
- `GET /api/supervisor-visits?awcCode=&status=&formStatus=&fromDate=&toDate=&full=true` - auto-scoped (block/district/sector see submitted visits)
- `GET /api/supervisor-visits/:id`
- `PATCH /api/supervisor-visits/:id/review` (block/district) - `{ status: "approved"|"rejected", remarks }`; a rejected visit can be corrected by the supervisor and goes back to pending
- `DELETE /api/supervisor-visits/:id` (supervisor, drafts only)

### Tasks
- `POST /api/tasks` (district/block/sector) — `{ title, description, dueDate, assignedToUser? , assignedToRole?, assignedToScopeCode? }` — assign to one user OR a whole role+scope group
- `GET /api/tasks?status=` — auto-scoped: your individual + group tasks, or ones you created
- `PATCH /api/tasks/:id/cancel` (creator only)

### Task Submissions
- `POST /api/task-submissions` (sector, awc) — `{ taskId, notes, checkInLatitude, checkInLongitude, photos }`
- `GET /api/task-submissions?taskId=&status=` — auto-scoped
- `PATCH /api/task-submissions/:id/review` (district/block/sector) — `{ status, remarks }`

### Grades — AWC performance, grade & district ranking
All routes need a token and are limited to the caller's scope (`req.scopeFilter`). Nothing is stored by hand:
every score is computed from real `Record`, `Task`/`TaskSubmission` and `SupervisorVisit` data.

- `GET /api/grades/ranking?period=YYYY-MM` — (district/block/supervisor/sector). Ranks **every AWC in the caller's scope together** (a district user gets all sectors of the district; sector is NOT required).
  Optional filters, freely combinable: `sectorCode`, `blockCode`, `grade` (`A+`,`A`,`B+`,`B`,`C`,`D`; send `A%2B` for `A+`), `search` (AWC name or code), `page` (default 1), `limit` (default 50, max 200), `districtCode` (must equal your own).
  Custom range instead of a month: `fromDate=YYYY-MM-DD&toDate=YYYY-MM-DD` (max 366 days). With neither, the current IST month is used.
  Response `data`: `period, periodType, scope, filters, summary { totalAWCs, totalRegisteredAWCs, awcsWithoutSubmissions, averageScore, aPlus, a, bPlus, b, c, d }, gradeDistribution { "A+":n, ... }, ranking[], pagination { page, limit, total, totalPages }`.
  Each ranking row: `rank` (position inside the sector/block being viewed, else the whole scope; **global across pages**), `overallRank` (position in the caller's whole scope), `awcCode, awcName, blockCode, blockName, sectorCode, sectorName, score, grade, metrics, metricsUsed, counts`.
- `GET /api/grades/top?period=YYYY-MM&limit=10` — top N of the same ranking (same filters).
- `GET /api/grades/awc/:awcCode?months=6&to=YYYY-MM` — month-by-month score, grade, **district rank**, metrics (newest first). `&stored=true` reads saved snapshots instead of computing live. An `awc` user can only open their own centre.
- `POST /api/grades/recalculate` (alias `POST /api/grades/generate`) — `{ period: "YYYY-MM" }` stores/refreshes the `Grade` snapshot + ranks for the whole district, or `{ period, awcCode }` for one AWC (its rank change is propagated to the others). Run it from a nightly job if you want stored history; live endpoints never need it.
- `GET /api/grades?period=YYYY-MM` — same as `/ranking`.

**Score (0–100)** = weighted average of five metrics (weights in `config/gradeConfig.js`):
Entry completion 30 (days with an entry ÷ expected working days, Sundays excluded, IST) · Entry quality 25 (approved ÷ approved+rejected) · Beneficiaries 20 (children attended ÷ registered on days the centre was open) · Tasks 15 (assigned tasks with an *approved* submission) · Inspection 10 (submitted, non-rejected supervisor visits where the centre was found open).
A metric that does not apply to an AWC that month (no task assigned, nothing reviewed yet, no inspection) is left out and the other weights are re-normalised, so it is never punished with a fake 0.
**Grade**: 90+ A+ · 80+ A · 70+ B+ · 60+ B · 50+ C · below 50 D (`calculateGrade` in `services/gradeService.js`).
**Rank**: score, then approval rate, completion, task completion, inspection (all high→low), then AWC code — so the order never changes between requests.
AWCs with no entry in the period are not scored or ranked; they are counted in `awcsWithoutSubmissions`.

Tests: `npm test` (needs a MongoDB on `mongodb://127.0.0.1:27017`, override with `GRADE_TEST_MONGO_URI`; set `GRADE_TEST_REAL_MONGO=1` when it is a real `mongod`, otherwise aggregation pipelines are evaluated with `mingo`).

### Notices — autogenerated
- `GET /api/notices?acknowledged=true|false` — auto-scoped; awc/sector see only their own
- `PATCH /api/notices/:id/acknowledge` — the notice's own recipient

### Reports
- `GET /api/reports/records/excel?fromDate=&toDate=` — downloads .xlsx
- `GET /api/reports/records/pdf?fromDate=&toDate=` — downloads .pdf
- `GET /api/reports/heatmap?period=YYYY-MM` — `{ points: [{ awcCode, awcName, latitude, longitude, totalScore, grade }] }` for map visualization

### Dashboard — computed sector-wise rollup
- `GET /api/dashboard?fromDate=&toDate=` — one row per sector, auto-scoped

### Users — team management
- `GET /api/users?role=&status=&search=`
- `POST /api/users` (district, block, sector — each can only create roles below their own) — `{ name, email, password, role, blockCode?, sectorCode?, awcCode? }`. Scope codes at-or-above the creator's own level are locked to the creator automatically (a block user can't plant a user in a different block); only pass the codes strictly below your own level. E.g. a block user creating an AWC only needs to send `sectorCode` + `awcCode` — `blockCode` is filled in from their own account.
- `PATCH /api/users/:id/status` (district/block/sector) — `{ status: "accepted"|"rejected" }`
- `DELETE /api/users/:id` (district, block, sector — same hierarchy rule as creation)

## Seeded demo data

`npm run seed` loads the real Dahod district sheet: **1 district, 21 blocks,
123 sectors, 3056 AWCs**, and creates one demo login per role (all share
password `Password@123`):

```
district -> district@dahod-demo.local
block    -> block@dahod-demo.local
supervisor -> supervisor-<sectorCode>@dahod-demo.local  (or login code SUP<sectorCode>)
sector   -> sector@dahod-demo.local
awc      -> awc@dahod-demo.local
```

The block/sector/awc demo users are all placed in the same real location from
the sheet (first block/sector/AWC), so they're guaranteed to line up with
each other for testing the full flow end to end.
